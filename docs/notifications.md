# Уведомления

## Новые сообщения на открытом сайте (SSE)

`GET /api/dialogs/events` работает в Node-runtime (`VINEXT_RUNTIME=node`), авторизуется через существующую HttpOnly-сессию и возвращает `text/event-stream` с приватным `no-store, no-transform`. На видимую вкладку приходится один общий `EventSource`. Скрытие вкладки и размонтирование закрывают соединение; возвращение открывает новое и получает актуальный счётчик. Если `EventSource` недоступен, HTTP-polling не включается.

Событие `unread` содержит `unreadCount`, включая начальный снимок. Событие `message` содержит только `dialogId` и `messageSeq`; оно показывает баннер «Новое сообщение» с переходом к диалогу. Снимок, собственные сообщения, повторы и входящие в уже открытый диалог баннер не показывают. Существующие индикаторы используют общий счётчик. Локальные `dogmeet-chat-changed` после прочтения/скрытия не вызывают дополнительный запрос: обновление приходит от сервера. Совместимый `GET /api/dialogs?unread=1` сохранён; polling истории и списка диалогов не менялся.

В процессе приложения используется один выделенный PostgreSQL-клиент `LISTEN dogmeet_chat`, общий для пользователей и вкладок, сохранённый при HMR. `pg_notify` вызывается внутри транзакций отправки, прочтения и скрытия: rollback и повтор `requestId` не создают нового входящего события. Payload проверяется и содержит только тип изменения, идентификаторы получателей/диалога и номер сообщения; текст, cookie и токены не передаются. Между процессами события доставляет PostgreSQL.

LISTEN и регистрация подписчика предшествуют снимку. Пересчёт выполняется последовательно на пользователя, объединяя одновременные запросы вкладок; результат, устаревший во время запроса, отбрасывается. Запрос считает только непрочитанные и ближайший срок их хранения. Одноразовый таймер обновляет счётчик при истечении исходных 72 часов без нового сообщения. Heartbeat раз в 25 секунд не читает БД. Медленный клиент закрывается при заполнении очереди из 16 кадров.

Последний подписчик освобождает LISTEN; новая подписка ждёт завершения предыдущего соединения. Потеря PostgreSQL-слушателя закрывает SSE-потоки, а браузер переподключается с интервалом 5 секунд. Повторный снимок восстанавливает счётчик: NOTIFY не хранит историю баннеров за время отключения. Поток ограничен пятью минутами или сроком сессии — после этого выполняются повторная авторизация и снимок; отзыв или замена сессии обнаруживаются не позднее этого срока. Завершение обновления сессии в текущей вкладке также переподключает общий источник.

Существующий локальный `Caddyfile` с `encode zstd gzip` и `reverse_proxy` не изменён. В проверке отдельным локальным Caddy-контейнером короткий SSE-кадр с этими заголовками пришёл сразу, первый байт через 0,05 секунды. Production и clipboard-конфигурация не затрагивались.

Проверки:

```sh
node --test server/infrastructure/chat-events.test.ts
CHAT_TEST_DATABASE_URL='postgresql://…@127.0.0.1:5432/testdb' node --test lib/chat-events.test.ts lib/dialogs.test.ts
PLAYWRIGHT_EXTERNAL_SERVER=1 pnpm exec playwright test e2e/chat-events.spec.ts e2e/chat.spec.ts e2e/chat-pet-selection.spec.ts
pnpm exec tsc --noEmit
pnpm lint
VINEXT_RUNTIME=node pnpm build
```

Интеграционный тест разрешает только локальный `CHAT_TEST_DATABASE_URL`, создаёт временную схему и удаляет её после проверки. Без переменной тест явно пропускается. Он проверяет настоящий HTTP-поток через отдельный vinext Node-сервер, транзакционный rollback, несколько вкладок/пользователей, прочтение, скрытие, истечение и восстановление LISTEN. Временное инструментирование pg живёт только в тестовом дочернем процессе и считает подключения/запросы без записи SQL и данных. Playwright отдельно проверяет интерфейс, дубли, видимость вкладки, смену сессии и отсутствие polling; подмена EventSource в UI-тестах не заменяет проверку реального endpoint.

Измерения локально 20.10.2026: до изменения в браузере было 5 запросов счётчика за 31 секунду; после — 0 и один запрос SSE. Отдельно 5 настоящих авторизованных вызовов старого GET создали 10 PostgreSQL-подключений и 10 SQL-запросов. Четыре SSE-потока трёх пользователей использовали один LISTEN; в реальном Node-потоке за 26 секунд простоя, включая heartbeat, было 0 SQL-запросов и 0 новых DB-подключений. CPU и RAM не измерялись. Миграция для SSE не требуется.

## Telegram-уведомления

Основная кнопка Telegram готовит ссылку для выбранного ЖК. Бот объясняет подписку на прогулки и личные сообщения; обе включаются кнопкой «Подписаться» в одной транзакции. Сам переход по ссылке согласия не даёт. Сообщение об успехе не содержит отписку.

В меню бота `/subscriptions` доступны «От прогулок» и «От сообщений». Первая показывает активные ЖК и отключает только выбранный ЖК. Вторая запрашивает подтверждение отписки от сообщений. После отключения всех ЖК сообщения продолжают приходить.

«Мой район и настройки» → «Уведомления» показывает статус сообщений:

- «Неизвестна» → «Проверить»: бот проверяет существующее согласие и связывает Telegram-личность с сессией сайта.
- «Неактивна» → «Подключить»: бот запрашивает согласие только на сообщения, без ЖК.
- «Активна» → «Отписаться»: бот запрашивает подтверждение отключения сообщений.

Сайт не меняет согласие через PATCH. Статус загружается при инициализации сессии и возврате по focus/visibilitychange, включая закрытую модалку, без polling. Обычный `/start` существующего подписчика открывает управление; ссылка с назначением открывает её сценарий. Проверка тоже передаёт непрозрачный токен параметром `start`, поддерживаемым Telegram deep link.

Нужны миграции `0048_telegram_chat_settings.sql` и `0050_telegram_subscription_purposes.sql` через существующий механизм. Новая добавляет назначение и время завершения намерения; существующие токены сохраняют общее назначение. Токен действует 15 минут, привязывается к первому приватному Telegram-чату и подтверждает изменение один раз. Повторное нажатие не восстанавливает отменённое согласие. Секреты не меняются.

Проверки:

```sh
node --test lib/telegram-chat.test.mjs lib/telegram-subscription-flow.test.mjs lib/telegram-subscriptions.test.ts lib/telegram.test.ts
pnpm exec tsc --noEmit
pnpm lint
pnpm exec playwright test e2e/telegram-notifications.spec.ts e2e/telegram-entry.spec.ts e2e/telegram-chat-link.spec.ts
```

Для SQL-теста доставки укажите `CHAT_TEST_DATABASE_URL` тестовой PostgreSQL-базы. Тест создаёт временную схему и удаляет её после проверки; без переменной пропускается. В Telegram передаются факт нового сообщения и имя отправителя; текст и доступ к диалогу остаются на сайте. Повтор сохранённого сообщения не создаёт второе уведомление. Сбой Telegram не отменяет сохранённое сообщение.
