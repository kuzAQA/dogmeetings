# План миграции фотографий питомцев

Статус на 4 октября 2026: инструмент реализован, обновление приложения развёрнуто на VDS; проба и полный dry-run завершены (10 фото, 964947 → 243803 байт, −74,7%, ошибок нет). Существующие фото не заменены; ожидается подтверждение записи и приостановки сервиса. Результаты: [pet-photo-migration-result.md](pet-photo-migration-result.md). Перед заменой существующих фотографий нужно отдельное разрешение на выполнение миграции с результатами пробного прогона. Работа только на VDS `185.75.189.36`, каталог `/opt/dogmeet`; локальные изменения сервера и Caddy сохраняются.

## Целевой алгоритм

Уточнение от 5 октября 2026: для новых загрузок на VDS применяется AVIF effort 2; ручная миграция v1 и её уже подготовленные кандидаты сохраняют effort 7. Существующие фото этим обновлением не заменялись.

Новые фото при создании и редактировании: `app/Home.tsx` → `preparePetPhoto()` → POST/PATCH `/api/pets` → `encodePetPhotoFile()` → PostgreSQL. Редактирование в админке: `app/dogsfather/page.tsx` → та же `preparePetPhoto()` → PATCH `/api/dogsfather/pets` → тот же серверный encoder.

В браузере JPEG/PNG/WebP больше 1600 px по длинной стороне уменьшаются до 1600 px с сохранением пропорций и округлением второй стороны; затем кодируются в WebP с quality 0.85. Маленькие фото отправляются без изменений. Сервер исправляет ориентацию, удаляет EXIF/GPS и сохраняет AVIF с `IMAGE_AVIF_QUALITY=40`, effort 7, chromaSubsampling 4:2:0, bitdepth 8. Сохраняется прозрачность; увеличение маленьких изображений исключено.

Лимиты новых загрузок: вход 20 × 1024² байт, результат 1 × 1024² байт, декодирование до 20 млн пикселей. Права и API-контракты сохраняются. Изменение полей питомца без выбора новой фотографии не перекодирует существующее фото.

Отдельные оригиналы в текущем хранилище не сохраняются: миграция использует уже сохранённые байты. Она не восстановит ранее утраченные детали, а повторное lossy-кодирование JPEG/WebP/AVIF может дополнительно изменить изображение. Поэтому исходные байты этого прогона сохраняются в резервной копии, а визуальная проверка выполняется до разрешения на запись.

На сервере при миграции браузера нет: реализовать эквивалентную последовательность через существующий Sharp. Для больших фото: ориентация → вычисление целевых размеров → resize → промежуточный WebP quality 85 → общий AVIF encoder. Для маленьких: ориентация → AVIF без resize и промежуточного WebP. Canvas и Sharp используют разные реализации ресэмплинга и WebP: совпадение выходных байтов не является критерием, проверяются размеры, прозрачность, отсутствие метаданных и визуальное качество.

Текущий `scripts/migrate-pet-photos.mjs` для этой задачи не подходит: он исключает `image/avif` и не уменьшает размеры. Не запускать его как миграцию на новый алгоритм. Новый инструмент реализован отдельно: `scripts/migrate-pet-photo-algorithm.mjs`; команды и условия запуска описаны в README.

## Порядок работ

1. **Инвентаризация и резервная копия.** Проверить checkout VDS и сохранить его локальные изменения без сброса файлов. Получить число фото, MIME и суммарный объём из `public.pets`; прочитать реальные размеры и формат через Sharp. Включить уже существующие AVIF, а не только JPEG/PNG/WebP. Создать отдельный защищённый каталог резервной копии, полный дамп PostgreSQL и проверить восстановление дампа в изолированной БД. Сохранить соответствие `id → photo, photo_type, updated_at` для выборочного отката. Не запускать ротацию резервных копий: текущий `scripts/backup.sh` удаляет копии старше 14 дней.

   Read-only SQL для инвентаризации:

   ```sql
   SELECT photo_type, count(*) AS photos,
          sum(octet_length(photo)) AS total_bytes,
          max(octet_length(photo)) AS largest_bytes
   FROM public.pets WHERE photo IS NOT NULL
   GROUP BY photo_type ORDER BY photo_type;
   ```

2. **Реализация и пробный прогон без изменения БД.** Добавить отдельную ручную миграцию, не автоматический шаг каждого запуска сайта. Принимать декодируемые JPEG/PNG/WebP и AVIF (Sharp: `heif` с compression `av1`); HEIF/HEIC с HEVC, анимации и неподдерживаемые файлы записывать как ошибки, не удаляя исходник. Обрабатывать последовательно, читать записи порциями по 10. Применять лимиты и общий AVIF encoder; не добавлять инфраструктуру очередей. До записи проверить возможность читать уже сохранённые AVIF и работу resize, ориентации, alpha и EXIF/GPS на тестах. Сначала провести пробу на 10 разнообразных фото, затем dry-run на всех фото. Сохранить готовые AVIF-кандидаты и приватный manifest: версия алгоритма, UUID, исходный SHA-256, целевой SHA-256, размеры, байты до/после, время и результат. Это позволяет применять уже проверенный результат и безопасно продолжать после сбоя без повторного lossy-кодирования. Все существующие фото, включая небольшие AVIF, обрабатываются один раз для этой версии алгоритма. Рост размера не скрывать: показать его в отчёте; результат больше 1 МиБ не применять. По фактическому времени dry-run оценить длительность записи и необходимое свободное место; сейчас количество фото на VDS неизвестно.

3. **Проверка результата и разрешение на запись.** Сравнить исходники и кандидаты: общий объём, МБ экономии, проценты, коэффициент уменьшения, число ошибок и фото с ростом размера. Просмотреть минимум 10 фото, включая вертикальные, прозрачные, маленькие и уже AVIF. Проверить декодирование, MIME `image/avif`, длинную сторону ≤1600 px, сохранение пропорций, отсутствие EXIF/GPS и лимит результата 1 МиБ. Список исключений должен быть явным; при ошибках не объявлять все фото мигрированными. После этого получить разрешение пользователя на конкретный объём замен и временную приостановку сервиса.

4. **Применение с защитой от потери новых правок.** На согласованное время остановить приложение и scheduler; БД оставить работающей. Применять только manifest этого прогона. Каждую запись обновлять в короткой транзакции: прочитать и заблокировать фото, сравнить исходный SHA-256, затем атомарно записать `photo`, `photo_type='image/avif'`, новый `updated_at`. Если текущий hash совпал с целевым — запись уже применена, пропустить. Если hash отличается от обоих — пользователь изменил фото после dry-run; не перезаписывать, вынести в новый прогон. Ошибка одной записи сохраняет её исходник и отражается в отчёте. URL сохраняется, новый `updated_at` меняет параметр `v` и предотвращает выдачу старой версии из кеша. Не изменять локальные Caddy-настройки и не обращаться к старому VDS.

5. **Проверка и откат.** Запустить приложение и scheduler, проверить `/api/pet-photo`: декодируемость, Content-Type, Content-Length, текущую версию URL, карточки и полные превью. Проверить создание и редактирование питомца новым фото, а также сохранение без замены фото. Сверить итоги с manifest: успешно применено, пропущено, конфликтов, ошибок, общий объём до/после. До принятия результата сохранить исходники и manifest вне автоматической ротации. При проблеме восстановить только фото, совпадающие с целевым hash manifest, не затрагивая последующие пользовательские изменения. При откате дать новый `updated_at`, чтобы кеш обновился. Полный дамп — резервный вариант для согласованного полного восстановления БД, а не обычный выборочный откат. Очистка резервных материалов выполняется только после отдельного подтверждения.

## Локальная проверка новых загрузок

```bash
pnpm check:pet-photo
pnpm exec playwright test e2e/pet-photo-upload.spec.ts --project=mobile
pnpm exec tsc --noEmit
```

Первые две команды проверяют реальные API handlers с изолированным адаптером хранения и браузерную загрузку. Они не подключаются к production-БД. Проведение миграции и проверка фактической PostgreSQL-записи на VDS остаются отдельной работой после согласования плана.
