# Включение уведомлений диалогов подписчикам прогулок при следующем обновлении VDS

**Статус:** частично выполнено 20.10.2026: код выпущен, подтверждённые связи обработаны; 6 из 8 активных Telegram-чатов остаются без доказанной связи с client_id.
**Когда:** обновление 20.10.2026 нового VDS `185.75.189.36`, проект `/opt/dogmeet`.
**Цель:** всем действующим подписчикам прогулок без уведомлений диалогов включить уведомления диалогов; при следующем входе с привязанного клиента сайт показывает «Активна».
**Основание:** прямой запрос владельца от 20 октября 2026 года. 20 октября владелец поручил выполнить план в составе обновления VDS.
**Подход:** разовый перенос данных с восстановлением только доказанных связей Telegram ↔ client_id. Использовать существующие настройки, API, интерфейс и штатный механизм миграций; не добавлять зависимости или отдельную систему подписок.

## 1. Контракты и границы

- `telegram_complex_subscriptions`: подписка на прогулки, ключ получателя `telegram_chat_id`, действующая подписка — `active = true`. Несколько ЖК одного чата не должны создавать дубликаты получателей. Наличие питомца и записи в `client_sessions` не является условием отбора.
- `telegram_chat_settings`: связь `client_id` → `telegram_chat_id`, `enabled` отвечает за уведомления диалогов. Существующий `enabled = false` у действующего подписчика прогулок входит в запрошенный разовый перенос. После переноса новое отключение пользователем обязательно сохраняется.
- `telegram_subscription_intents`: дополнительное свидетельство связи только при непустых `client_id`, `used_by_chat_id` и `used_at`. Непогашенная ссылка не доказывает принадлежность Telegram-чата. Истечение срока уже использованной ссылки само по себе не отменяет установленную связь; штатная очистка могла удалить такие записи.
- `lib/telegram-chat.ts` читает настройку по текущему `client_id`; `app/api/telegram/notifications/route.ts` возвращает `enabled/subscribed/status`. `app/features/telegram/useTelegramSettings.ts` загружает статус при входе, фокусе и возврате вкладки; `app/features/home/components/WalksWorkspace.tsx` показывает «Активна». Отправка сообщения в Telegram также требует связи получателя диалога с `client_id`.
- Ограничение идентификации: по одному Telegram ID нельзя автоматически определить браузер пользователя. Не создавать случайные client_id, не привязывать по имени/контакту питомца и не считать миграцию полностью выполненной, если остались чаты без доказанной связи. Новый браузер или потерянная cookie требуют существующего Telegram-подтверждения; автоматически показать ему личную подписку безопасно невозможно.

Никаких сообщений подписчикам без отдельного поручения владельца. Нулевое число нерешённых чатов — условие полного выполнения требования «всем»; при ненулевом числе согласовать способ восстановления до объявления переноса завершённым.

Начальный read-only отчёт, который не теряет подписчиков из-за отсутствия сессий:

```sql
WITH active_chats AS (
    SELECT DISTINCT telegram_chat_id
    FROM telegram_complex_subscriptions
    WHERE active = true
)
SELECT a.telegram_chat_id,
       COUNT(t.client_id) AS linked_clients,
       COUNT(t.client_id) FILTER (WHERE t.enabled) AS enabled_clients
FROM active_chats a
LEFT JOIN telegram_chat_settings t USING (telegram_chat_id)
GROUP BY a.telegram_chat_id
ORDER BY a.telegram_chat_id;
```

ON CONFLICT (client_id) DO NOTHING`, не перезаписывая существующую принадлежность. Не фильтровать по наличию сессии/питомца. Не восстанавливать отсутствующие `client_sessions`: это отдельные секреты аутентификации, а не реестр Telegram-подписок.
- [x] Включить все существующие и восстановленные связи активных чатов: `UPDATE telegram_chat_settings SET enabled = true WHERE enabled = false AND EXISTS (SELECT 1 FROM telegram_complex_subscriptions s WHERE s.telegram_chat_id = telegram_chat_settings.telegram_chat_id AND s.active = true)`. Не менять выключенные настройки чатов без действующей подписки прогулок, самих подписок прогулок или уже включённые настройки.
- [x] Разовый запуск контролирует `public.app_migrations`; не включать этот UPDATE при каждом запуске сервера, в scheduler, GET статуса или общем Telegram-flow. Сам SQL должен выдерживать повтор внутри проверки без дублей, но эксплуатационно его нельзя повторять после пользовательской отписки. Не менять поведение будущих подписок в рамках этой задачи.
- [x] Проверить существующую цепочку API → hook → меню для перенесённого client_id. Ожидаемый ответ: `{ enabled: true, subscribed: true, status: "active" }`; после открытия сайта/возврата вкладки меню показывает «Активна». Менять UI только если поведенческий тест выявит реальный дефект этой цепочки; не ставить статус локально и не выдавать «Активна» без настройки на сервере.

Обязательные сценарии integration-теста: активный чат с выключенной настройкой включается; несколько ЖК не дают дублей; уже включённая настройка сохраняется; неактивный/отсутствующий walk subscriber остаётся выключенным; отсутствующая связь восстанавливается по использованному intent; неиспользованный intent не подходит; однозначный истёкший, но использованный intent подходит; отсутствие client_sessions не исключает настройку; несколько client_id одного чата обрабатываются; конфликтующие исторические связи не перепривязываются. Дополнительно: повтор миграции не создаёт дубликатов, а повтор штатного migrate после пользовательского отключения не включает настройку заново.
